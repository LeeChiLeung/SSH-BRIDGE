## Context

项目底层已经支持 `--ssh-password` 参数，SSH 连接逻辑也能够使用密码进行认证，但当前 WebUI 的 profile 表单只暴露了私钥路径，导致浏览器端无法配置密码认证。与此同时，底层如果同时拿到密码和私钥，认证策略需要统一成确定行为，避免运维人员误判实际使用了哪一种凭据。

这次变更跨越 Web 表单、profile 映射和 SSH 认证逻辑，属于一条完整的用户路径调整，适合先明确数据流和优先级规则，再进入实现。

## Goals / Non-Goals

**Goals:**
- 让 WebUI 可以录入 SSH 密码并用于隧道启动。
- 明确运行时认证顺序为：密码非空时优先密码认证，密码为空时才使用私钥。
- 保持 CLI 参数能力不变，并让 Web 路径与 CLI 路径在底层共享一致的认证规则。
- 尽量减少对现有 profile 使用方式的干扰。

**Non-Goals:**
- 不在本次变更中引入密码加密存储、密钥环集成或外部 secrets 管理。
- 不改变现有 `--ssh-password` CLI 入口或私钥认证能力。
- 不扩展到多因素认证、agent forwarding 或交互式密码提示。

## Decisions

### 1. Web profile 数据模型直接增加密码字段
Web 层会为 profile 表单、请求解析和配置映射新增 SSH 密码字段，使浏览器侧能够显式提交密码，并传递给运行时的 `TunnelConfig`.

Rationale:
- 这是最直接的数据路径，代码改动集中，容易测试。
- 可以保持 CLI 和 Web 最终都汇总到同一个配置结构。

Alternatives considered:
- 只在启动时临时输入密码，不保存到 profile；这样更安全，但与当前“保存并复用 profile”的使用方式不一致，也会增加交互复杂度。

### 2. 认证方法选择规则以密码优先为准
当配置中同时存在密码和私钥路径时，运行时只优先使用密码认证；当密码为空时才回退到私钥认证。

Rationale:
- 这与用户要求一致，规则简单明确。
- 避免多种鉴权方式同时尝试，减少连接行为不透明的问题。

Alternatives considered:
- 同时追加密码和私钥到认证方法列表，让服务端自行决定；这样兼容性更高，但与“优先密码”的要求不一致，也不利于预期管理。

### 3. 先满足功能，再在规格中显式承认密码存储风险
本次只实现功能，不做加密存储；设计文档和规格会明确这是当前折中。

Rationale:
- 用户当前明确需要 WebUI 密码输入能力。
- 现有 profile 机制本就是本地 JSON 文件持久化，本次不额外引入新基础设施。

Alternatives considered:
- 在本次同时引入本地加密或系统凭据库；这会显著扩大实现范围，不适合当前变更。

## Risks / Trade-offs

- [密码持久化到本地 profile 文件带来明文风险] → 在文档和界面说明中明确当前行为，后续可单独规划加密存储变更。
- [已有 profile 不包含密码字段] → 通过零值兼容处理，旧 profile 继续可读可用。
- [同时配置密码和私钥时行为变化] → 以规格和 UI 文案明确“密码优先”，并补充测试覆盖。

## Migration Plan

这次变更无需数据迁移。已有 `profiles.json` 在新增密码字段后应继续兼容读取；未填写密码的旧 profile 将继续走私钥认证路径。

## Open Questions
