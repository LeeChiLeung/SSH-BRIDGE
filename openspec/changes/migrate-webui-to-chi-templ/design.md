## Context

项目当前的 Web 控制台集中在 `web.go` 中实现，包含 HTTP 路由、HTML 模板、CSS、前端脚本和页面数据结构。这个结构在功能探索阶段很高效，但已经开始显著制约后续工作，尤其是中英切换、组件复用、模板可读性和分阶段重构。

用户已经明确希望保留现有 `web.go` 不立即删除，而是在根目录新增 `ui/`，用 `chi + templ` 重构部分前端界面。这意味着本次不是单纯的换框架，而是要定义一套可并存、可切换、可渐进迁移的 UI 架构。

## Goals / Non-Goals

**Goals:**
- 建立新的 `ui/` 服务端 UI 层，承载后续界面重构和国际化扩展。
- 使用 `chi` 改善路由组织，使用 `templ` 改善组件化和模板维护性。
- 保留现有 `web.go` legacy 控制台，避免一次性替换全部页面。
- 明确业务核心的单一来源：新旧 UI 必须共用同一套 controller、profile store 和状态模型。
- 为后续逐页迁移提供明确路径，比如先迁移首页卡片，再迁移详情和表单。

**Non-Goals:**
- 不在本次方案中引入 React、Vue 或前后端分离架构。
- 不在第一次重构中要求所有现有页面一次性迁移完成。
- 不复制一份新的隧道控制逻辑或 profile 管理逻辑到 `ui/`。
- 不在本次方案中同时完成完整国际化实现，只为其预留结构。

## Decisions

### 1. 新旧 UI 双栈并存，legacy 保留到迁移完成
新 UI 会放在 `ui/` 目录下，legacy `web.go` 保留作为可回退实现。程序需要支持明确切换到新 UI 或 legacy UI，而不是在迁移初期直接删除旧页面。

Rationale:
- 当前 legacy UI 已可用，能降低重构期风险。
- 渐进迁移比一次性重写更容易验证行为一致性。

Alternatives considered:
- 直接在 `web.go` 原地拆分；成本低，但不能解决模板和组件长期维护问题。
- 一次性重写整个 WebUI；结构更干净，但回归风险过高。

### 2. `ui/` 只承载表现层，不复制业务内核
`ui/` 目录只负责新的路由适配、页面组件、静态资源和文案组织。隧道控制、profile 存储、运行状态、日志与指标仍然复用现有 Go 核心模块。

Rationale:
- 可以保证新旧 UI 的行为一致。
- 避免重构演变成两套系统并存。

Alternatives considered:
- 给新 UI 单独做一套 view-model 和控制层；这样灵活，但很容易与原逻辑漂移。

### 3. 先定义目录和切换入口，再逐页迁移
第一次实施应优先建立 `ui/router.go`、页面/组件目录、基础 layout、静态资源加载和主程序切换入口。功能页面采用分阶段迁移，而不是要求在建立骨架时就全部迁完。

Rationale:
- 先打通骨架，后迁页面，能让后续迭代更平滑。
- 也有利于国际化在新 UI 中从一开始按组件化方式落地。

Alternatives considered:
- 先迁一个页面但不搭整体骨架；短期见效快，但会反复返工目录和接口。

### 4. 新 UI 默认使用服务端渲染和轻量前端增强
即使使用 `chi + templ`，新 UI 仍然保持服务端渲染为主，少量 JS 增强交互，不走前端单页应用路线。

Rationale:
- 与项目当前的本地控制台定位一致。
- 便于打包、调试和跨平台交付。

Alternatives considered:
- 进一步引入 SPA 或 API-first 前端；这超出当前项目的必要复杂度。

## Risks / Trade-offs

- [新旧两套 UI 并存时间过长，维护成本上升] → 在 tasks 中要求定义明确迁移阶段和退出条件，避免无限期双栈。
- [chi/templ 引入新的开发工具链] → 控制范围在 UI 层，并把生成与构建流程文档化。
- [UI 重构过程中行为与 legacy 偏离] → 强制共用 controller/store 内核，并优先迁移最可验证的页面。
- [国际化需求推高重构范围] → 本次只建立适合国际化的结构，不要求一次完成所有多语言能力。

## Migration Plan

1. 保持现有 `web.go` 作为默认稳定实现或可显式启用的 legacy 实现。
2. 在 `ui/` 中建立 `chi + templ` 骨架、layout 和切换入口。
3. 先迁移列表首页或其他低风险页面，验证新结构可用。
4. 逐步迁移详情、表单、日志面板和局部交互。
5. 当新 UI 覆盖主要使用路径并达到行为对齐后，再考虑下线 legacy UI。
