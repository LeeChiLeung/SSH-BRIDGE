## Context

项目已经在 `ui/` 目录下建立了基于 `chi + templ` 的新控制台，并明确把它作为后续界面演进的主线。此前的重构方案已经要求新 UI 对国际化友好，但当前仍缺少一套真正可用的多语言实现：页面文案分散在模板和处理器中，用户也没有显式的语言切换入口。

这次变更的范围聚焦在新的 `chi + templ` 控制台，不要求 retrofitting legacy `web.go`。用户目标也很明确：补上日语翻译，并在页面上提供切换按钮，让三语界面可以直接使用和验证。

## Goals / Non-Goals

**Goals:**
- 为新的 WebUI 提供中文、英文、日语三套可切换文案。
- 在页面显著位置提供语言切换按钮，并在切换后立即影响当前页面与后续页面。
- 建立统一的字典访问方式，让列表、详情、表单和状态文本都从同一套 i18n 层取值。
- 让所选语言在刷新页面、切换详情和表单提交后保持一致。

**Non-Goals:**
- 不改造 legacy `web.go` 的旧控制台国际化。
- 不在本次引入第三方前端 i18n 框架或浏览器端大型状态管理。
- 不要求首轮就把所有后端错误字符串都翻译为三语，只覆盖 WebUI 自身可控文案和常见状态描述。

## Decisions

### 1. 采用服务端轻量字典层，而不是引入额外 i18n 框架
新 UI 继续保持服务端渲染主导，因此国际化实现也保持在 Go 侧：定义语言标识、字典映射和 `T(key)` 风格的访问层，由 handler 把当前语言注入页面渲染上下文。

Rationale:
- 与 `chi + templ` 的当前结构一致，复杂度最低。
- 便于把文案控制在仓库内部，不引入额外构建流程。

Alternatives considered:
- 引入浏览器端 i18n 库；不符合当前项目的轻量控制台定位。
- 在模板里直接写多语言分支；会快速失控，难维护。

### 2. 语言选择以“显式切换 + cookie 持久化 + 默认回退”实现
用户点击语言按钮后，服务端写入语言 cookie，并在后续页面渲染时优先读取该值。若用户尚未显式选择，则按应用默认语言回退；如有需要，可在后续扩展对 `Accept-Language` 的更细分支持。

Rationale:
- 页面刷新、详情切换、表单提交后都能自然保持语言。
- 对当前本地控制台足够稳定，且不依赖复杂前端状态同步。

Alternatives considered:
- 只用 query 参数；跨页面跳转时容易丢失。
- 只靠浏览器 `Accept-Language`；无法满足用户主动切换。

### 3. 切换入口放在新控制台的稳定公共区域
语言切换按钮应位于页面公共头部或工具栏，而不是埋在某个详情页或设置页内。按钮使用简洁的 `中文 / EN / 日本語` 文本形式，确保首轮可用性优先。

Rationale:
- 所有页面都可见，符合频繁切换验证场景。
- 不需要额外图标资产或复杂交互。

Alternatives considered:
- 放进配置页；入口过深，不利于发现。
- 仅使用下拉菜单；可做，但当前按钮切换更直接。

### 4. 优先清理新 UI 中硬编码文案，建立可扩展 key 命名
本次不仅补字典，还要把新 UI 里已有的硬编码文案统一收敛到 key-based 字典层，按模块组织 key，例如 `home.title`、`detail.status`、`form.save`。

Rationale:
- 如果只是追加日语字符串而不收敛文案来源，后续扩展会继续恶化。
- 后续新增语言时只需要补字典，不必继续拆模板。

Alternatives considered:
- 只翻译表面文案，暂时保留硬编码；短期快，但很快会返工。

## Risks / Trade-offs

- [新 UI 里仍有遗漏的硬编码文案] → 通过任务明确覆盖列表、详情、表单和共用按钮，并在实施时做一次集中扫描。
- [语言状态在局部请求或重定向中丢失] → 统一使用 cookie 持久化，并要求所有重定向返回到带当前语言上下文的页面。
- [日语文案长度导致布局挤压] → 首轮使用文本按钮并在现有布局上做最小样式校正，优先避免按钮换行和表头错位。
- [后端原始错误消息仍然是单语] → 当前只规范 WebUI 自身可控文本，对底层原始错误先保留，后续如有需要再包一层本地化摘要。

## Migration Plan

1. 在 `ui/` 中建立或补齐统一的 locale 类型、字典和翻译访问入口。
2. 为新 UI 公共 layout 增加语言切换按钮和当前语言状态。
3. 逐页替换首页列表、详情面板、编辑/新增弹层中的硬编码文案。
4. 校正重定向、表单提交和局部刷新逻辑，确保语言在交互后不丢失。
5. 保持 legacy 控制台不变，仅在新 UI 路径中启用该能力。

## Open Questions

- 语言默认值最终固定为中文，还是允许后续再接入基于浏览器头的自动初始判断。
- 是否在这次顺手把底层常见错误类型映射成可翻译的用户态错误摘要。
