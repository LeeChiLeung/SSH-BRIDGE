## Context

当前新控制台已经成为主 WebUI，首页具备 profile 列表、详情、创建、编辑、启动和停止能力，但 profile 数据仍然局限于本机配置文件。项目已经有 `ProfileStore` 负责持久化、`ui/` 负责新控制台页面和动作处理，因此导入/导出能力需要同时覆盖存储层、HTTP 接口和前端交互。

导入操作相比导出更复杂，因为它不仅涉及文件读取，还涉及 profile 名称冲突、字段合并策略、错误反馈以及用户确认步骤。这个需求跨越数据模型、Web 交互和页面状态管理，适合先形成明确设计再进入实现。

## Goals / Non-Goals

**Goals:**
- 提供一套稳定的 JSON 导出格式，用于备份和跨机器迁移 profile。
- 在新控制台首页新增导出与导入入口，并支持文件下载/上传。
- 导入时按隧道名称识别冲突，并向用户提供“跳过”或“合并”的明确选择。
- 保证导入流程不会在未确认的情况下覆盖现有 profile。

**Non-Goals:**
- 不在本次变更中支持 CSV、YAML 或其他导出格式。
- 不引入复杂的逐字段冲突解决 UI；“合并”以预定义规则执行。
- 不处理密码加密、远程同步、云端配置中心等更大范围的配置管理能力。
- 不修改旧 `web.go` 控制台的交互，优先覆盖 `ui/` 新控制台。

## Decisions

### 1. 使用单文件 JSON 作为导入导出载体
导出文件包含版本号、导出时间和 profile 数组。这样后续如果 schema 扩展，可以通过版本字段兼容旧文件。

备选方案：
- 直接导出 `profiles.json` 原始内部结构：实现简单，但会把存储细节暴露为外部契约，不利于后续演进。
- 一次一个 profile：适合分享单条配置，但不满足备份/迁移主要场景。

### 2. 冲突检测以“Title/隧道名称”作为主键
用户明确要求“同样的隧道名称的配置”触发冲突，因此导入预检查以 `Profile.Title` 为匹配键。若导入文件中 title 为空，则视为非法项并在预检查阶段报错。

备选方案：
- 以 profile ID 匹配：内部稳定，但导入到另一台机器时 ID 常常不具备业务意义，也不符合用户心智。
- 以 SSH 地址和本地端口联合匹配：有一定合理性，但不符合本次需求中的“同名配置”定义。

### 3. “导入”采用两阶段流程：预检查，再确认执行
第一阶段上传 JSON 并返回解析结果，包括新增项、冲突项和非法项。第二阶段由用户选择冲突处理策略后提交正式导入。这样可以避免上传即写入，降低误覆盖风险。

备选方案：
- 一次提交直接导入：实现更短，但不满足用户在冲突时“选择是否跳过、合并”的交互要求。

### 4. “合并”采用已有 profile 保留 ID，导入 profile 覆盖可编辑字段
当用户选择合并时，现有 profile 保留其内部 ID 和运行时关联，标题作为同名键保持不变；其余可编辑字段由导入项覆盖，包括 SSH 参数、本地/远程端口、超时、known_hosts 与 host key 校验选项。

备选方案：
- 保留现有字段、仅补缺失字段：风险较小，但用户更难预期最终结果。
- 每个字段逐项让用户确认：更精确，但明显超出当前轻量控制台范围。

## Risks / Trade-offs

- [冲突键只使用 title，可能出现“同名但其实不是同一条隧道”] → 在预检查结果中明确展示冲突项，并要求用户显式选择跳过或合并。
- [导入文件 schema 后续演进可能导致兼容性问题] → 在导出文件顶层加入 schema version，导入端按版本校验。
- [合并会覆盖密码、私钥路径等敏感配置] → 在确认界面中明确说明“合并会使用导入文件覆盖现有配置字段”。
- [首页按钮和确认弹层会增加 UI 状态复杂度] → 复用现有 modal/页面状态模式，不新增前端框架。
